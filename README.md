# ТЗ на АИС «Абонемент» для МБУК «ЦБС г. Энска»

Техническое задание на создание автоматизированной информационной системы «Абонемент» для МБУК «ЦБС г. Энска».

> Проект учебный. Все организации и люди в материалах вымышлены.

## Что в репозитории

### `sources/` — исходные материалы

Markdown-версии документов, на основании которых разрабатывается ТЗ: приказ о создании системы, протоколы интервью, служебная записка о защите информации и ПДн, справка об ИТ-инфраструктуре, описание процессов «как есть», положение об обслуживании читателей, статистика, глоссарий заказчика и шаблон ТЗ. Всего 12 документов, номера `SRC-01`…`SRC-12`. Реестр с авторами и датами — в [`sources/README.md`](sources/README.md).

В требованиях ТЗ на документы ссылаются по номеру, например `[SRC-09, п. 3.2]`. Файлы в `sources/` не редактируются: исправления и толкования вносятся в ТЗ, в глоссарий или в журнал решений.

## Как ведётся работа

- ТЗ ведётся в Markdown по ГОСТ 34.602-2020 и хранится в Git.
- Один раздел — один файл.
- Ветки: `main` — согласованный текст ТЗ; каждая правка делается в отдельной ветке с именем `tz/<раздел>-<тема>` латиницей; в `main` правки попадают только по [правилам команды](#правила-команды).
- Коммиты в `main` и в ветках, где работают другие, не переписываются: ошибку в общей истории исправляет новый или отменяющий коммит (revert).
- Свою ветку до слияния автор может переписать (исправляющий коммит, перенос), если ею никто не пользуется; отправка — только `git push --force-with-lease`. Принудительная отправка в `main` запрещена.
- Открытый вопрос к заказчику заводится задачей на GitHub с меткой «ОВ» и вносится в приложение А (`tz/a-open-questions.md`).
- Замечание к тексту ТЗ заводится задачей с меткой «замечание»; запрос на слияние с правкой содержит в описании строку `Closes #N`, и задача закрывается при слиянии.
- В коммитах и запросах на слияние по открытому вопросу указывается только `Refs #N`, пока нет решения заказчика.
- Заказчик получает DOCX и PDF, собранные из текста.
- Оригиналы исходных документов хранятся как есть, а в `sources/` лежат их Markdown-версии для работы.

## Правила команды

Владельцы файлов заданы в `.github/CODEOWNERS`. Правка попадает в `main` только через запрос на слияние, а запрос сливается, только когда прошли автоматические проверки markdown и docx из `.github/workflows/ci.yml`.

| Что меняется | Владельцы | Автор правки | Кто одобряет | Кто сливает |
|---|---|---|---|---|
| Все файлы, кроме перечисленных ниже | ведущий аналитик, команды func-analysts и sec-analysts | любой участник команды | владелец этих файлов, кроме автора | ведущий аналитик после одобрения |
| `tz/04-2-functions.md` (раздел 4.2) | Анна, команда func-analysts, ведущий аналитик | любой участник команды | владелец этих файлов, кроме автора | ведущий аналитик после одобрения |
| `tz/04-1-structure.md`, `tz/04-3-support.md`, `tz/04-4-general-tech.md` (разделы 4.1, 4.3, 4.4) | Борис, команда sec-analysts, ведущий аналитик | любой участник команды | владелец этих файлов, кроме автора | ведущий аналитик после одобрения |
| `.github/` (правила и шаблоны) | ведущий аналитик | любой участник команды | владелец этих файлов, кроме автора | ведущий аналитик после одобрения |

Ведущий аналитик сливает запрос коммитом слияния.

Если одобрить некому (например, правку в `.github/` делает сам ведущий аналитик), ведущий аналитик сначала пишет причину комментарием в этом запросе, затем сливает запрос в обход правил. Недоступный владелец — не повод обходить правила: запрос ждёт его.
